# FLEXIBLE QUEST ITEMS ANALYSIS — 다중 허용 제출 아이템

기준일: **2026-08-08**

## 결론

최신 regular Quest 데이터에서 한 `giveItem` 목표가 여러 Item ID를 허용하는 경우는 **3건뿐**입니다.

이 구조를 별도의 `A를 선택 / B를 선택` 사용자 상태로 만들지 않습니다.

준현 헬퍼에서는 이를 **유동 제출 목표**로 해석합니다.

> 한 퀘스트 목표가 여러 종류의 Item ID를 허용하고, 그 허용 아이템들의 보유량을 합쳐 하나의 요구 수량을 충족한다.

따라서 프로그램은 사용자의 선택을 영구 저장하지 않고 현재 Inventory에서 허용 아이템의 합계를 매번 계산합니다.

## 실제 데이터 규모

regular source snapshot에서:

- 전체 Quest: 510개
- 필수 `giveItem` 제출 목표: 187개
- 허용 Item ID가 2개 이상인 제출 목표: **3개**

확인된 형태:

| Quest ID | 목표 요구량 | FIR | 허용 Item ID 수 |
| --- | ---: | --- | ---: |
| `64916b6286c03d0e2d4f5f55` | 1 | Yes | 2 |
| `5c51aac186f77432ea65c552` | 50 | No | 5 |
| `64d0b40fbe2eed70e254e2d4` | 5 | No | 3 |

`5c51aac186f77432ea65c552`는 현재 데이터에서 Collector에 해당합니다.

## 계산

예:

```text
A / B / C 중 총 5개 제출

보유:
A 2
B 1
C 0

→ 유동 제출 진행 3 / 5
→ 2개 더 필요
```

FIR 목표라면 허용 후보들의 FIR 보유량만 FIR 충족에 사용합니다.

## 왜 사용자 선택을 저장하지 않는가

이 목표는 미래의 특정 아이템 하나를 미리 골라 고정해야 하는 제품 상태가 아닙니다.

사용자 선택을 별도로 저장하면:

- 실제 게임에서는 다른 허용 아이템으로 제출할 수 있는데 헬퍼가 불필요하게 선택을 고정할 수 있음
- 패치로 허용 아이템 목록이 바뀌면 선택 상태 migration 문제가 생김
- Inventory라는 이미 존재하는 사용자 사실과 별도의 중복 상태가 생김

따라서 `현재 Game Content의 허용 Item IDs + 현재 Inventory`만으로 진행도를 계산합니다.

## 정리 필요와의 관계

유동 제출 그룹에서 각 후보의 `정리 가능` 수량은 서로 독립적으로 더할 수 없습니다.

예:

```text
A / B 중 5개 필요
보유 A 5, B 5
```

- A 5개를 버리고 B 5개를 남기는 것은 가능
- B 5개를 버리고 A 5개를 남기는 것도 가능
- 하지만 A 5개와 B 5개를 동시에 `각각 정리 가능`이라고 표시하면 전부 버릴 수 있다는 잘못된 안내가 됨

따라서 해당 Quest가 완료되기 전까지는 후보 Item별 자동 cleanup을 계속 보호합니다.

대신 사용자에게는 그룹 단위로:

- 허용 아이템 목록
- 총 필요량
- 현재 합산 보유량
- 남은 필요량
- FIR 필요 여부

를 보여주는 것이 안전합니다.

## 구현 원칙

- 별도 사용자 선택 상태 없음
- `QuestItemRequirement` 원천 데이터가 진실의 기준
- `FlexibleQuestItemRequirementCalculator`가 Inventory를 합산해 현재 진행도를 계산
- 후보 Item별 cleanup은 기존 보호 규칙 유지
- Quest 완료 시 해당 목표 자체가 미래 계획에서 빠지므로 보호도 자연스럽게 사라짐
- 패치로 accepted Item IDs가 바뀌면 별도 migration 없이 새 Game Content + 기존 Inventory로 다시 계산

이 구조는 **데이터에서 계산 가능한 것을 사용자에게 다시 입력시키지 않는다**는 준현 헬퍼의 유지보수 원칙과 일치합니다.
