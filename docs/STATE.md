## 프로젝트 이름

**준현 헬퍼**

저장소: `Propeex/JunhyunHelper`

## 프로젝트 목표

사용자와의 대화를 통해 준현 헬퍼를 처음부터 제품 설계하고, 대화가 바뀌어도 저장소만으로 같은 개발 방향을 복구할 수 있게 합니다.

## 현재 확정된 핵심 원칙

- 공식 제품명은 **준현 헬퍼**입니다.
- 기존 `Propeex/Tarkov-Helper`는 필요할 때만 참고하며 정답이나 제품 사양으로 간주하지 않습니다.
- 사용자는 의도와 피드백을 구두로 전달할 수 있고 개발자가 이를 구조화합니다.
- 구두 설명은 개발자 해석 → 사용자 교정 → 작동 방식 협의 후에만 공식 요구사항으로 확정합니다.
- 제품 경험에 영향을 주는 선택은 사용자와 협의하고, 구현 세부사항은 개발자가 책임집니다.
- 대화 간 연속성은 GitHub 공식 문서로 유지합니다.
- 제품 설계가 충분히 진행되기 전에는 제품 코드를 작성하지 않습니다.
- 현재 제품 발견 단계에서는 **한 기능의 세부사항을 끝까지 파기보다 모든 핵심 기능의 큰 틀을 먼저 정합니다.**
- 전체 기능의 역할과 관계가 보인 뒤 필요한 기능부터 세부 UX, 예외, 보정 규칙으로 내려갑니다.

## 퀘스트 기능 — 현재 확정된 큰 틀

- 최신 퀘스트 원천 데이터는 `json.tarkov.dev`에서 받고 준현 헬퍼 내부 모델로 변환합니다.
- PvP, PvE, 시즌 계열 등 서로 다른 게임 모드의 캐릭터는 **서로 독립된 진행 프로필**로 관리합니다.
- 각 진행 프로필에 해당 캐릭터의 레벨, 진영, 필요한 상인 상태, 에디션, 프레스티지, 완료 퀘스트 등 해금 판정에 필요한 정보를 저장할 수 있어야 합니다.
- 전체 퀘스트 중 현재 선택된 진행 프로필이 **선행 조건을 만족한 미완료 퀘스트**를 자동 계산하여 보여줍니다.
- 실제 게임의 `잠김 → 수주 가능 → 진행 중` 중 준현 헬퍼는 수주 가능한 퀘스트를 모두 수락한다고 가정합니다.
- 준현 헬퍼의 핵심 퀘스트 상태는 `잠김 → 현재 퀘스트 → 완료`입니다.
- 사용자가 게임에서 퀘스트를 완료하면 준현 헬퍼에서도 완료 처리하고 후속 퀘스트 판정을 갱신합니다.
- 퀘스트 목록은 장소(맵) 또는 상인 기준으로 분류할 수 있어야 합니다.
- 퀘스트를 선택하여 설명/목표 등 클리어에 필요한 정보와 Wiki 페이지를 확인할 수 있어야 합니다.
- `AvailableAfter` 같은 **시간 지연 해금은 구현하지 않습니다.** 실제 완료 시각을 알 수 없으므로 잘못된 동기화를 만드는 것보다, 다른 조건을 만족한 순간 현재 퀘스트로 보여주는 것을 선택했습니다.
- 따라서 시간 지연이 있는 일부 퀘스트가 실제 게임보다 일찍 표시될 수 있으며 이는 의도된 차이입니다.
- 퀘스트 화면의 시각적 레이아웃은 현재 제품 설계에서 확정하지 않고 구현 단계로 미룹니다.

## 현재 확인된 퀘스트 선행 조건 계열

- 캐릭터 레벨
- 진영(BEAR/USEC)
- 선행 퀘스트 상태
- 상인 평판(Standing)
- 상인 로열티 레벨(Loyalty Level)
- 게임 에디션/버전 제한
- 프레스티지
- 선택된 게임 모드에 따른 퀘스트 데이터
- 이벤트/시즌 등 전역 노출 조건(안정적으로 판정 가능한 경우)

시간 지연 조건은 제품 결정으로 제외합니다.

## 퀘스트에서 현재 미룬 세부사항

아래는 필요하지만 **지금 당장 큰 틀을 정하는 데 필수적이지 않아 후속 상세 설계로 미룹니다.**

- `json.tarkov.dev`가 실제 해금 조건을 어디까지 직접 제공하는지 최종 검증
- 실패 상태나 분기형 선행 조건의 세부 동기화 방식
- 완료 처리 취소 및 오입력 복구 방식
- API 갱신/캐시/오프라인 정책
- 진행 프로필의 구체적인 입력 화면
- 퀘스트 화면의 정확한 레이아웃과 조작 방식

## 다른 기능

은신처, 필요 아이템, 탄약 표, 지도, RatScanner의 실제 작동 방식은 아직 의도 정렬 단계입니다.

1. 퀘스트 기능은 현재 확보한 큰 틀에서 일단 멈춥니다.
2. 다음 핵심 기능의 목적과 큰 동작을 사용자와 맞춥니다.
3. 은신처, 필요 아이템, 탄약 표, 지도까지 큰 틀을 확보합니다.
4. 이후 전체 기능 간 공통 데이터와 관계를 검토합니다.
5. 그 다음 필요한 기능부터 세부 UX/예외/검증 기준으로 내려갑니다.
6. 제품 요구가 충분히 정의되기 전에는 제품 코드를 작성하지 않습니다.
