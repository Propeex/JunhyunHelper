# STATE — 현재 프로젝트 상태

> 이 문서는 새 개발자가 가장 빠르게 현재 상태를 복구하기 위한 핸드오프 문서입니다.

## 현재 Phase

**Phase 1 — 제품 발견(Product Discovery) 및 요구사항 설계**

상태: `IN PROGRESS`

Phase 0의 프로젝트 기억/개발 운영 구조는 완료되었습니다. 제품 코드는 아직 작성하지 않습니다.

## 프로젝트 목표

새로운 Tarkov Helper를 사용자와의 대화를 통해 **처음부터 제품 설계**하고, 이후 개발자가 바뀌거나 대화가 바뀌어도 저장소만으로 맥락을 복구하여 동일한 방향으로 개발을 이어갈 수 있게 합니다.

## 현재 확정된 핵심 원칙

- `CONFIRMED` 새 Tarkov Helper는 처음부터 제품 설계합니다.
- `CONFIRMED` 기존 `Propeex/Tarkov-Helper`는 필요할 때만 참고합니다.
- `CONFIRMED` 기존 구현을 정답이나 제품 사양으로 간주하지 않습니다.
- `CONFIRMED` 사용자는 제품 의도와 피드백을 전달하고, 개발 세부 절차는 개발자가 담당합니다.
- `CONFIRMED` 대화 간 연속성은 GitHub 저장소의 공식 문서와 변경 이력을 통해 유지합니다.
- `CONFIRMED` 제품 설계가 충분히 진행되기 전에는 제품 코드 구현을 시작하지 않습니다.

## 준비 완료된 기억/개발 구조

- `README.md` — 프로젝트 진입점
- `AGENTS.md` — 개발자/AI 운영 규약과 대화 간 복구 절차
- `docs/STATE.md` — 현재 상태/핸드오프
- `docs/PRODUCT.md` — 제품 정의와 요구사항
- `docs/DECISIONS.md` — 확정 결정 이력
- `docs/ARCHITECTURE.md` — 기술 설계
- `docs/DEVELOPMENT.md` — 개발/검증/인수인계 절차
- `docs/REFERENCE_POLICY.md` — 기존 구현 참고 규칙

## 현재까지 하지 않은 것

- 제품 기능 정의
- 화면/UX 설계
- 데이터 소스 선정
- 기술 스택 확정
- 아키텍처 확정
- 제품 코드 작성
- 기존 Tarkov-Helper 코드 분석

이는 의도된 상태입니다. 기존 구현을 먼저 분석해 새 제품의 사고방식을 오염시키지 않기 위해, 사용자 문제와 제품 동작을 먼저 정의합니다.

## 바로 다음 행동

1. 사용자에게 실제 Tarkov 사용 상황을 듣습니다.
2. “무슨 기능이 필요한가”보다 먼저 “어떤 순간에 어떤 문제를 해결해야 하는가”를 구체화합니다.
3. 대표 사용 장면을 `FLOW-XXX` 형태의 핵심 사용 흐름으로 정리합니다.
4. 그 흐름에서 제품이 책임져야 할 판단/정보/입력/출력을 도출합니다.
5. 확정 내용은 `PRODUCT.md`, 장기적인 방향 결정은 `DECISIONS.md`에 반영합니다.
6. 제품 요구가 충분히 정의되기 전에는 기술 스택이나 구현 구조를 확정하지 않습니다.

## 현재 열린 질문

- `OPEN` 사용자가 Tarkov Helper를 실제로 사용하는 핵심 상황은 무엇인가?
- `OPEN` 그 상황에서 지금 가장 불편하거나 시간이 많이 드는 일은 무엇인가?
- `OPEN` 프로그램이 대신 판단해야 하는 것과 단순히 정보를 보여줘야 하는 것은 각각 무엇인가?

## 다음 대화의 첫 질문

**Tarkov를 하면서 “이건 프로그램이 대신 해줬으면 좋겠다”고 느끼는 가장 대표적인 장면 하나를 실제 상황처럼 설명해 주세요.**

가능하면 기능 이름보다, 그때 무엇을 보고 있고 무엇을 판단하려 하며 지금은 어떻게 처리하는지를 먼저 파악합니다.
