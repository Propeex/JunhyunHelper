# MAINTENANCE PHILOSOPHY — 준현 헬퍼 유지보수 철학

이 문서는 준현 헬퍼가 기능이 늘어나더라도 불필요하게 복잡해지지 않도록 지켜야 할 설계 원칙을 정의합니다.

상태: `CONFIRMED`

## 1. 기본 관점

준현 헬퍼는 본질적으로 복잡한 제품이 아닙니다.

핵심은 다음과 같습니다.

`최신 Tarkov 데이터 다운로드 → 준현 헬퍼 내부 데이터로 변환 → 사용자 진행 상태와 결합 → 필요한 정보 계산/조회`

구현 구조가 이 제품 원리보다 훨씬 복잡해지면 설계가 잘못된 신호로 봅니다.

## 2. 단순성을 기능 수보다 우선한다

- 미래에 필요할지 모르는 기능을 위해 미리 복잡한 추상화를 만들지 않습니다.
- 실제로 두 번째 구현이 필요해지기 전까지 범용 프레임워크를 만들지 않습니다.
- 단순한 기능에 manager/service/coordinator 계층을 여러 겹 추가하지 않습니다.
- 클래스 수나 디자인 패턴 사용량을 품질의 척도로 보지 않습니다.
- 같은 목적을 더 적은 상태와 더 적은 연결로 달성할 수 있으면 단순한 쪽을 선택합니다.

## 3. 게임 데이터와 사용자 진행 데이터를 분리한다

### 게임 데이터

패치에 따라 바뀌며 온라인 원천에서 다시 만들 수 있는 데이터입니다.

예:

- 퀘스트 정의
- 퀘스트 조건
- 아이템 정의
- 은신처 시설/레벨/요구사항
- 탄약 성능 및 수급 관계
- 상인/맵 등 참조 데이터

이 데이터는 필요하면 삭제하고 API에서 다시 구축할 수 있어야 합니다.

### 사용자 진행 데이터

사용자가 실제 게임에서 만든 상태이며 다시 다운로드할 수 없는 데이터입니다.

예:

- 캐릭터 프로필
- 레벨/진영/에디션/프레스티지
- 상인 진행 상태
- 완료 퀘스트
- 은신처 현재 레벨
- 보유 아이템 수량

게임 데이터 갱신이 사용자 진행 데이터를 수정하거나 위험하게 만들면 안 됩니다.

## 4. 계산 가능한 파생 상태는 가능한 한 저장하지 않는다

같은 사실을 원본 상태와 계산 결과로 중복 저장하면 동기화 문제가 생깁니다.

따라서 다음과 같은 값은 기본적으로 현재 원본 상태에서 계산합니다.

- 퀘스트의 `현재 가능/잠김` 여부
- 현재 필요한 아이템 수량
- 퀘스트/은신처별 남은 필요량
- 화면에 표시하기 위한 집계값

성능상 캐시가 필요해지는 경우에도 캐시는 진실의 원천이 아니며 언제든 재생성 가능해야 합니다.

## 5. 하나의 사실은 한 시스템만 판단한다

동일한 규칙을 여러 화면이나 서비스에서 다시 구현하지 않습니다.

예:

- 퀘스트 해금 여부 → Quest 계산 로직이 한 번 판단
- 은신처 다음 요구사항 → Hideout 계산 로직이 판단
- 필요 아이템 집계 → Needed Items 계산 로직이 판단
- 데이터 형식 해석 → 해당 Importer가 판단

UI는 이 결과를 표시하고 사용자 입력을 전달합니다. UI가 게임 규칙을 별도로 해석하지 않습니다.

## 6. 기능 간 의존 방향은 한쪽으로 흐르게 한다

핵심 시스템은 부가 기능을 몰라야 합니다.

허용되는 방향 예:

- Needed Items → Quest/Hideout 결과 사용
- Map → Quest/Item 정보를 조회
- Scanner → Item/Needed Items 정보를 조회

금지되는 방향 예:

- Quest가 Items 화면을 직접 수정
- Needed Items가 Quest 완료 상태를 직접 변경
- Map이 Quest 내부 저장 구조를 수정
- Scanner가 자체 퀘스트 계산 로직을 보유

지도나 Scanner를 제거해도 퀘스트/은신처/필요 아이템 기능이 영향 없이 동작해야 합니다.

## 7. 화면은 비즈니스 로직의 주인이 아니다

화면 코드는 다음에 집중합니다.

- 사용자 입력 받기
- 조회 결과 표시
- 사용자 명령 전달

다음은 화면에서 직접 하지 않습니다.

- 외부 API JSON 해석
- SQL을 이용한 게임 규칙 판정
- 퀘스트 선행 조건 계산
- 필요 아이템 집계
- 데이터 업데이트/교체 절차
- 여러 기능의 상태를 직접 맞추는 동기화

거대한 MainWindow/Page code-behind 형태의 중앙 집중 구조를 만들지 않습니다.

## 8. 이벤트 연쇄보다 명시적 호출과 재계산을 선호한다

기능 A의 변경이 이벤트 B를 발생시키고 B가 C/D/E를 다시 갱신하는 식의 긴 연쇄는 피합니다.

사용자 상태가 바뀌면 필요한 기능이 해당 상태를 읽어 결과를 다시 계산하는 단순한 흐름을 선호합니다.

이벤트가 필요한 경우에도:

- 책임이 명확해야 함
- 구독 수명주기가 분명해야 함
- 같은 사실을 동기화하기 위한 이벤트 남발을 금지함

## 9. 외부 API는 경계에서만 다룬다

외부 데이터는 각 Importer에서 내부 모델로 변환한 뒤 프로그램 안으로 들어옵니다.

제품 로직은 `json.tarkov.dev`의 필드명이나 원본 JSON 구조를 알 필요가 없어야 합니다.

외부 스키마가 바뀌면 가능한 한 Importer와 Validator만 수정하면 되도록 합니다.

## 10. 실패는 조용한 오염보다 명확한 중단을 선택한다

데이터 업데이트가 실패하면:

- 불완전한 새 DB를 활성화하지 않음
- 기존 정상 DB 유지
- 사용자 진행 데이터는 건드리지 않음
- 원인을 진단할 수 있는 정보 기록

`업데이트 실패`는 허용할 수 있지만 `틀린 데이터를 정상처럼 사용하는 상태`는 허용하지 않습니다.

## 11. 기존 Tarkov-Helper 재사용 원칙

기존 `Propeex/Tarkov-Helper`를 구현의 출발점으로 삼지 않습니다.

순서는 항상 다음과 같습니다.

1. 준현 헬퍼 요구사항으로 독립 설계
2. 새 설계의 위험/빈틈 검토
3. 기존 프로젝트의 실패 사례와 회수 후보 확인
4. 새 설계에 실제로 도움이 되는 원리/테스트/소형 부품만 선택
5. 필요하면 준현 헬퍼 구조에 맞게 재작성

즉 `기존 코드 → 수정해서 사용`이 기본이 아니라 `새 설계 → 필요한 경험만 회수`가 기본입니다.

## 12. 유지보수 가능성 검사 질문

새 기능이나 구조를 추가할 때 개발자는 최소한 다음을 확인합니다.

1. 이 상태를 정말 저장해야 하는가, 계산할 수는 없는가?
2. 같은 규칙을 이미 다른 곳에서도 판단하고 있지 않은가?
3. 이 기능이 다른 기능의 내부 구현을 알아야 하는가?
4. 이 계층/서비스가 실제로 독립적인 책임을 갖는가?
5. 이 기능을 삭제했을 때 핵심 시스템까지 무너지는가?
6. 외부 API 변경이 UI까지 전파되는 구조인가?
7. 데이터 업데이트 실패가 기존 정상 데이터나 사용자 데이터를 훼손할 수 있는가?
8. 지금 필요한 문제를 해결하는가, 미래를 상상해 만든 복잡성인가?

하나라도 좋지 않은 답이 나오면 구조를 다시 단순화합니다.
