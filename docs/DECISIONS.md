- 이유: 사용자는 실제로 수주 가능한 퀘스트를 모두 수락할 예정이며, 게임과 헬퍼에서 같은 수락 작업을 반복할 필요가 없다.

- 영향: 준현 헬퍼의 핵심 퀘스트 상태는 `잠김 → 현재 퀘스트 → 완료`로 단순화된다. 현재 퀘스트는 해금 조건을 만족하고 아직 완료되지 않은 퀘스트다.

- 상태: `CONFIRMED`

- 이유: 실제 게임에서도 모드별 캐릭터는 레벨, 퀘스트 진행, 평판, 은신처 등 진행 상태가 서로 다른 별도 캐릭터다.
- 대안/배경: `게임 모드`를 하나의 프로필 필드로 두고 진행 상태를 공유하는 방식은 실제 게임 구조와 맞지 않는다.
- 영향: 퀘스트 완료 상태와 캐릭터 진행 정보는 선택된 게임 진행 프로필에 귀속한다. 다른 캐릭터 종속 기능도 같은 원칙을 우선 적용한다.
- 대체한 결정: DEC-011의 과거 `게임 모드`를 프로필 내부 조건값처럼 본 해석을 명확히 수정한다.

- 날짜: 2026-08-08

- 영향: 시간 지연 외의 확인 가능한 선행 조건을 모두 만족한 미완료 퀘스트는 준현 헬퍼에서 현재 퀘스트로 간주한다. 이 때문에 시간 지연이 있는 일부 퀘스트는 실제 게임보다 일찍 표시될 수 있으며 이는 의도된 근사 동작이다.

- 날짜: 2026-08-08
- 결정: GPT/개발자는 외부 API 데이터의 의미와 변환 규칙을 개발 시점에 설계·구현하고, 이후 일반적인 패치 데이터 갱신은 준현 헬퍼가 온라인 데이터를 직접 내려받아 동일한 규칙으로 내부 데이터베이스를 재구축하도록 한다.
- 이유: 패치마다 GPT가 새 데이터를 다시 해석하고 프로그램용 데이터로 수작업 변환해야 한다면 제품이 GPT와 개발자 작업에 지속적으로 종속되고 유지보수 비용이 커진다.
- 대안/배경: `새 데이터 → GPT 해석 → 프로그램에 새 데이터 전달` 방식을 채택하지 않는다.
- 영향: 런타임/일반 데이터 업데이트 경로에는 GPT 의존성이 없어야 한다. 변환 규칙은 프로그램 코드와 검증 가능한 내부 모델로 구현한다.
- 대체한 결정: DEC-009의 퀘스트 전용 변환 원칙을 제품 전체 데이터 아키텍처 원칙으로 확장한다.

## DEC-016 — 핵심 데이터 영역은 퀘스트·은신처·탄약이며 필요 아이템은 파생 데이터로 만든다

- 상태: `CONFIRMED`
- 날짜: 2026-08-08
- 결정: 현재 핵심 데이터베이스 업데이트 범위는 퀘스트, 은신처, 탄약으로 한다. 필요 아이템 목록은 별도 고정 데이터가 아니라 최신 퀘스트 요구 아이템과 은신처 업그레이드 요구 아이템에서 계산해 만든다.
- 이유: 사용자가 실제로 필요한 핵심 기능은 최신 데이터베이스 유지와 그 데이터에서 필요한 정보를 파생해 쓰는 것이다.
- 대안/배경: 필요 아이템을 패치마다 별도 수작업 데이터베이스로 관리하는 방식은 중복과 불일치를 만든다.
- 영향: 퀘스트/은신처 데이터가 갱신되면 필요 아이템도 같은 내부 데이터에서 다시 계산되어 자동으로 최신화되어야 한다. 지도는 아직 API 공급원을 확보하지 않아 이 확정 데이터 파이프라인에서 제외한다.
- 대체한 결정: 없음

## DEC-017 — 외부 API 스키마는 안정적일 수 있지만 불변으로 가정하지 않는다

- 상태: `CONFIRMED`
- 날짜: 2026-08-08
- 결정: 게임 데이터의 값과 내용 변경은 자동으로 흡수하되, 외부 API의 데이터 형식 자체가 영원히 동일하다고 가정하지 않는다. 데이터 갱신 전 스키마/필수 필드를 검증하고 비호환 변경을 감지해야 한다.
- 이유: API의 핵심 필드가 삭제되거나 타입/의미가 바뀐 상황에서 기존 변환기를 강제로 적용하면 조용히 잘못된 내부 데이터베이스를 만들 수 있다.
- 대안/배경: 모든 미래 API 응답이 현재 형식과 동일하다고 전제하고 무조건 파싱하는 방식은 채택하지 않는다.
- 영향: 호환 가능한 데이터 내용 변화는 자동 업데이트한다. 비호환 스키마 변화 시에는 갱신을 안전하게 중단하고 마지막 정상 데이터를 보호하며, 필요한 경우 변환 코드 자체를 업데이트한다.
- 대체한 결정: 없음
