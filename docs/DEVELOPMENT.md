# DEVELOPMENT — 개발 및 검증 절차

이 문서는 사용자가 개발 세부 절차를 직접 관리하지 않아도 개발자가 일관된 방식으로 작업하기 위한 운영 규칙입니다.

## 1. 기본 작업 흐름

의미 있는 변경은 다음 순서를 기본으로 합니다.

1. 현재 저장소 상태 복구
2. 관련 사용자 의도/요구사항 확인
3. 미확정 사항과 확정 사항 구분
4. 필요한 경우 제품/기술 설계 갱신
5. 구현
6. 자동/수동 검증
7. 제품 요구사항과 실제 동작 비교
8. 공식 문서와 `STATE.md` 갱신
9. 다음 개발자가 바로 이어갈 수 있는 상태로 종료

## 2. 구현 시작 조건

기능 구현 전 최소한 다음이 정의되어야 합니다.

- 사용자에게 왜 필요한가
- 어떤 상황에서 사용되는가
- 입력은 무엇인가
- 기대 출력/동작은 무엇인가
- 실패하면 어떻게 보여야 하는가
- 어떤 데이터에 의존하는가
- 완료 여부를 어떻게 검증하는가

이 조건이 부족하면 코드를 먼저 작성하지 않고 제품 설계를 보완합니다.

## 3. 변경 단위

가능하면 한 변경은 하나의 명확한 목적을 가집니다.

예:

- 한 제품 요구사항 추가
- 한 기능 구현
- 한 데이터 공급원 변경
- 한 버그 수정
- 한 구조 개선

서로 관련 없는 변경을 한꺼번에 섞지 않습니다.

## 4. 브랜치/PR/CI

GitHub의 세부 개발 절차는 개발자가 관리합니다.

사용자에게 브랜치, PR, CI에 대한 운영 판단을 요구하지 않습니다. 다만 다음과 같이 제품에 영향을 주는 경우에는 사용자에게 설명합니다.

- 요구사항이 바뀌는 경우
- 기존 동작을 의도적으로 제거하는 경우
- UX가 달라지는 경우
- 정확도/성능/보안 사이의 중요한 절충이 필요한 경우

## 5. 검증 원칙

### 기능 검증

기능은 코드가 실행된다는 이유만으로 완료되지 않습니다. 관련 `REQ-XXX`의 검증 기준을 만족해야 합니다.

### 회귀 검증

기존 확정 동작을 변경하는 경우 의도하지 않은 영향이 없는지 확인합니다.

### 데이터 검증

게임 데이터 또는 외부 데이터에 의존하는 기능은 다음을 확인합니다.

- 데이터 출처
- 데이터 버전/갱신 시점
- 누락/오류 가능성
- 캐시/갱신 규칙
- 출처 장애 시 동작

### 사용자 검증

UX 또는 제품 판단이 중요한 변경은 기술적으로 성공했더라도 사용자의 피드백을 받아 최종 방향을 확정할 수 있습니다.

## 6. 완료(Definition of Done)

기능은 필요한 범위에서 아래를 충족할 때 완료로 봅니다.

- 확정 요구사항과 동작이 일치함
- 실패/예외 동작이 정의됨
- 필요한 테스트/검증을 통과함
- 오래된 가정이나 검증되지 않은 기존 코드에 의존하지 않음
- 관련 문서가 실제 구현과 일치함
- `STATE.md`가 다음 작업을 정확히 가리킴

## 7. 문서 갱신 규칙

문서는 코드와 별개의 장식물이 아닙니다.

- 제품 방향 변경 → `PRODUCT.md`, 필요 시 `DECISIONS.md`
- 장기 결정 변경 → `DECISIONS.md`
- 기술 구조 변경 → `ARCHITECTURE.md`
- 현재 작업 상태 변경 → `STATE.md`
- 기존 구현을 참고한 중요한 판단 → 필요 시 `REFERENCE_POLICY.md` 원칙에 따라 근거 기록

## 8. 대화가 바뀔 때의 복구 기준

새 대화의 개발자는 이전 대화 내용을 기억한다고 가정하지 않습니다.

저장소 문서를 읽은 뒤 다음 네 질문에 답할 수 있어야 합니다.

1. 지금 무엇을 만들고 있는가?
2. 왜 그렇게 만들기로 했는가?
3. 어디까지 완료됐는가?
4. 다음에 무엇을 해야 하는가?

답할 수 없다면 먼저 문서/이력을 조사하고, 필요 시 상태 문서를 보완합니다.
