# PRODUCT — 준현 헬퍼 제품 정의

이 문서는 **무엇을 만들고 왜 만드는지**를 정의하는 제품의 공식 제품 설계 문서입니다.

사용자가 구두로 전달한 아이디어는 곧바로 완성된 요구사항으로 간주하지 않습니다. 먼저 원래 의도를 기록하고, 개발자의 해석을 사용자와 맞춘 뒤, 실제 작동 방식까지 합의된 내용만 `CONFIRMED` 요구사항으로 승격합니다.

## 1. 제품 이름

`CONFIRMED`

**준현 헬퍼**

저장소 이름은 `JunhyunHelper`이지만 사용자에게 보이는 공식 제품명은 **준현 헬퍼**입니다.

## 2. 제품의 현재 이해

`INTENT_CAPTURED`

준현 헬퍼는 Escape from Tarkov 플레이를 보조하기 위한 데스크톱 헬퍼 프로그램입니다.

현재 사용자가 제시한 주요 기능 영역은 퀘스트 목록, 은신처 목록, 필요 아이템, 탄약 표, 지도, RatScanner 기능 통합입니다.

이 문장은 **현재까지 전달받은 방향을 요약한 것**이며, 각 기능의 의미·사용 상황·세부 동작이 모두 확정되었다는 뜻은 아닙니다.

## 3. 대상 사용자

`CONFIRMED`

최초 설계 기준 사용자는 이 프로젝트의 사용자 본인입니다. 일반 사용자 확장 여부는 이후 별도로 결정합니다.

## 4. 사용자에게서 직접 전달받은 초기 기능 의도

아래 항목은 아직 정식 요구사항이 아니라 **구두 의도를 보존하기 위한 출발점**입니다.

### FEATURE-001 — 퀘스트 목록

- 상태: `CONFIRMED / 상세 설계 진행 중`
- 사용자는 자신의 Tarkov 진행 상태를 기준으로 현재 실제 게임에서 수주 가능한 퀘스트를 보고 싶어 합니다.
- 준현 헬퍼에서는 수주 가능한 퀘스트를 사용자가 곧바로 수락한다고 가정하여, 별도의 수락 조작 없이 현재 진행 가능한 퀘스트 목록으로 취급합니다.
- 사용자는 퀘스트를 완료 처리할 수 있어야 하며, 완료 상태는 이후 퀘스트 해금 판정에 반영됩니다.
- 퀘스트 상세 화면과 분류/탐색 UX는 계속 협의합니다.

### FEATURE-002 — 은신처 목록

- 상태: `INTENT_CAPTURED`
- 사용자는 은신처 시설 목록을 볼 수 있기를 원합니다.
- 사용자는 시설 레벨을 설정할 수 있기를 원합니다.
- 어떤 정보와 조작 방식이 필요한지는 아직 사용자와 맞춰야 합니다.

### FEATURE-003 — 필요 아이템

- 상태: `INTENT_CAPTURED`
- 은신처 업그레이드 및 퀘스트에 필요한 아이템 목록을 다루는 기능입니다.
- 사용자는 각 아이템의 보유 개수를 추가할 수 있기를 원합니다.
- 필요 수량 계산, 진행도 반영, 분류, 표시 방식 등은 아직 사용자와 맞춰야 합니다.

### FEATURE-004 — 탄약 표

- 상태: `INTENT_CAPTURED`
- 사용자는 구경별 탄약 목록을 확인하고 싶어 합니다.
- 각 탄약의 정보와 수급처 등을 표로 확인하고 싶어 합니다.
- 정확한 정보 항목과 실제 사용 방식은 아직 사용자와 맞춰야 합니다.

### FEATURE-005 — 지도

- 상태: `INTENT_CAPTURED`
- 사용자는 지도에서 각종 정보를 확인하고 싶어 합니다.
- 지도를 미니맵 형식으로 띄워 인게임 중에도 사용하고 싶어 합니다.
- 지도 정보의 종류, 조작 방식, 미니맵의 동작은 아직 사용자와 맞춰야 합니다.

### FEATURE-006 — RatScanner 기능 통합

- 상태: `INTENT_CAPTURED / LATER`
- 사용자는 RatScanner의 기능을 준현 헬퍼로 옮기고 싶어 합니다.
- 현재 RatScanner 원본 프로그램이 정상 작동하지 않아 실제 통합은 후속 단계로 계획합니다.
- 어떤 RatScanner 기능을 유지할지와 구현 방식은 추후 별도로 협의·조사합니다.

## 5. 제품 설계 방식

각 기능은 다음 순서로 설계합니다.

1. 사용자가 기능의 목적과 원하는 경험을 구두로 설명합니다.
2. 개발자가 자신의 이해를 제품 관점에서 다시 설명합니다.
3. 사용자가 잘못 이해한 부분과 빠진 부분을 교정합니다.
4. 실제 작동 방식을 대화로 구체화합니다.
   - 언제 사용하는가
   - 무엇을 보는가
   - 무엇을 입력/조작하는가
   - 프로그램이 무엇을 판단/계산하는가
   - 무엇을 화면에 보여주는가
   - 다른 기능과 어떤 관계가 있는가
   - 어떤 예외 상황이 있는가
5. 의미와 동작이 충분히 맞았을 때만 정식 Flow와 Requirement를 `CONFIRMED`로 기록합니다.

## 6. 핵심 사용 흐름

### FLOW-001 — 현재 가능한 퀘스트 확인 및 완료 동기화

- 상태: `CONFIRMED`
- 시작 상황: 사용자가 준현 헬퍼의 퀘스트 기능을 엽니다.
- 사용자 목표: 실제 게임에서 현재 수행할 수 있는 퀘스트와 준현 헬퍼의 목록을 일치시키고, 필요한 정보를 확인합니다.
- 사용자의 입력/행동: 사용자 프로필 정보를 관리하고, 게임에서 퀘스트를 완료하면 준현 헬퍼에서도 해당 퀘스트를 완료 처리합니다.
- 프로그램의 동작: 전체 퀘스트 데이터와 사용자 프로필/완료 기록을 비교해 현재 해금 조건을 만족하면서 미완료인 퀘스트를 계산합니다.
- 프로그램의 출력: 현재 사용자가 실제 게임에서 수주 가능한 퀘스트를 준현 헬퍼에서는 이미 수락된 현재 퀘스트로 보여줍니다.
- 예외/보정: 실제 게임과 목록이 다를 경우 사용자의 프로필 정보 또는 완료 기록을 수정하여 다시 동기화할 수 있어야 합니다.
- 완료 조건: 실제 게임에서 퀘스트 완료 → 준현 헬퍼에서 완료 처리 → 후속 퀘스트 해금 판정에 즉시 반영됩니다.

## 7. 제품 요구사항

### REQ-001 — 현재 퀘스트 자동 판정

- 상태: `CONFIRMED`
- 사용자 의도: 전체 퀘스트가 아니라 현재 자신의 캐릭터가 실제 게임에서 수행할 수 있는 퀘스트만 보고 싶습니다.
- 요구 동작: 준현 헬퍼는 퀘스트의 선행 조건과 사용자 프로필/완료 상태를 비교하여 현재 수주 가능한 미완료 퀘스트를 자동 계산해야 합니다.
- 수락 처리: 게임의 `잠김 → 수주 가능 → 진행 중` 상태 중, 준현 헬퍼는 사용자가 수주 가능한 퀘스트를 모두 수락한다고 가정하여 `수주 가능`과 `진행 중`을 별도로 추적하지 않습니다.
- 결과 상태: 준현 헬퍼 관점의 핵심 상태는 `잠김 → 현재 퀘스트 → 완료`입니다.
- 관련 Flow: `FLOW-001`

### REQ-002 — 퀘스트 완료 동기화

- 상태: `CONFIRMED`
- 사용자 의도: 인게임 진행도와 준현 헬퍼의 퀘스트 목록을 맞추고 싶습니다.
- 요구 동작: 사용자가 퀘스트를 완료 처리하면 해당 완료 상태를 저장하고, 그 완료가 선행 조건인 후속 퀘스트의 해금 판정을 다시 계산해야 합니다.
- 관련 Flow: `FLOW-001`

### REQ-003 — 퀘스트 판정용 사용자 프로필

- 상태: `CONFIRMED`
- 사용자 의도: 게임 캐릭터의 실제 상태를 준현 헬퍼에 입력하여 인게임과 같은 퀘스트 목록을 보고 싶습니다.
- 요구 동작: 사용자 프로필에는 퀘스트 해금/노출 조건을 판정하는 데 필요한 사용자 상태를 입력·수정할 수 있어야 합니다.
- 현재 명시된 예: 레벨, 진영, Fence 우호도, 게임 모드(PvP/PvE/시즌 계열), 게임 에디션, 프레스티지 횟수, 완료 퀘스트.
- 확장 원칙: 실제 최신 퀘스트 데이터에서 추가 조건이 확인되면 해당 조건을 판정할 수 있도록 프로필 항목을 확장합니다. 필요하지 않은 값을 근거 없이 먼저 추가하지 않습니다.
- 관련 Flow: `FLOW-001`

### REQ-004 — 퀘스트 원천 데이터 변환 계층

- 상태: `CONFIRMED`
- 사용자 의도: 최신 퀘스트 데이터를 활용하되 준현 헬퍼에 맞는 형태로 안정적으로 사용하고 싶습니다.
- 요구 동작: `json.tarkov.dev`에서 퀘스트 데이터를 받아 준현 헬퍼 내부 퀘스트 모델로 변환한 뒤 제품 기능에서 사용합니다. 제품 로직이 외부 API 원본 구조에 직접 종속되지 않도록 합니다.
- 관련 Flow: `FLOW-001`

## 8. 퀘스트 표시/탐색에서 현재 합의된 방향

- 현재 퀘스트 목록은 장소(맵) 또는 상인 기준으로 분류해서 볼 수 있어야 합니다.
- 사용자는 퀘스트를 선택하여 퀘스트 설명, 목표 등 클리어에 필요한 정보를 확인할 수 있어야 합니다.
- 사용자는 해당 퀘스트의 Wiki 페이지를 열 수 있어야 합니다.
- 정확한 목록 레이아웃, 필터 UI, 상세 화면 정보 우선순위는 계속 협의합니다.

## 9. 기능 간 관계

현재: `OPEN`

퀘스트, 은신처, 필요 아이템 등이 서로 연결될 가능성은 있으나, 연결 방식은 사용자와 기능별 작동을 먼저 맞춘 뒤 정의합니다.

기존 Tarkov-Helper의 연동 방식을 기본값으로 삼지 않습니다.

## 10. 비목표(Non-goals)

현재 퀘스트 기능에서는 다음을 기본적으로 하지 않습니다.

- 인게임에서 퀘스트를 `Accept`했는지 별도로 추적하지 않습니다.
- 사용자가 준현 헬퍼에서 퀘스트마다 별도의 `수락` 버튼을 누르도록 요구하지 않습니다.

그 외 비목표는 계속 설계하면서 추가합니다.

## 11. UX 원칙

현재 퀘스트 기능에서 확인된 원칙:

- 인게임과 준현 헬퍼를 맞추기 위해 필요한 사용자 입력을 최소화합니다.
- 프로그램이 데이터와 프로필로 계산할 수 있는 상태는 자동으로 계산합니다.
- 사용자는 실제 게임에서 발생한 핵심 상태 변화(예: 퀘스트 완료)를 준현 헬퍼에 반영하는 데 집중합니다.

## 12. 정보 정확성 원칙

`CONFIRMED`

- 기존 Tarkov-Helper에 표시되거나 구현되어 있다는 이유만으로 정보를 사실로 간주하지 않습니다.
- 게임 정보가 제품 동작에 영향을 주는 경우 출처와 갱신 방식을 별도로 정의해야 합니다.
- 불확실하거나 오래될 수 있는 정보는 검증 없이 제품 규칙으로 고정하지 않습니다.
- RatScanner 또한 원본 구현을 그대로 정답으로 복제하지 않고, 사용자에게 필요한 기능을 다시 정의한 뒤 준현 헬퍼 설계에 맞게 통합합니다.
