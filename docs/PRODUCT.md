# PRODUCT — 준현 헬퍼 제품 정의

이 문서는 **무엇을 만들고 왜 만드는지**를 정의하는 공식 제품 설계 문서입니다.

사용자가 구두로 전달한 아이디어는 곧바로 완성된 요구사항으로 간주하지 않습니다. 개발자가 이해한 내용을 사용자와 맞추고 실제 작동 방식까지 합의된 내용만 `CONFIRMED` 요구사항으로 기록합니다.

## 1. 제품 이름

`CONFIRMED`

**준현 헬퍼**

저장소 이름은 `JunhyunHelper`이지만 사용자에게 보이는 공식 제품명은 **준현 헬퍼**입니다.

## 2. 제품의 현재 이해

준현 헬퍼는 Escape from Tarkov 플레이를 보조하기 위한 데스크톱 헬퍼 프로그램입니다.

현재 논의 중인 주요 기능 영역은 퀘스트 목록, 은신처 목록, 필요 아이템, 탄약 표, 지도, RatScanner 기능 통합입니다.

각 기능은 사용자 의도 확인 → 개발자 해석/역제안 → 사용자 교정 → 작동 방식 합의 → 공식 요구사항 기록 순서로 설계합니다.

## 3. 대상 사용자

`CONFIRMED`

최초 설계 기준 사용자는 이 프로젝트의 사용자 본인입니다. 일반 사용자 확장 여부는 이후 별도로 결정합니다.

## 4. 기능 영역

### FEATURE-001 — 퀘스트 목록

- 상태: `CONFIRMED / 상세 설계 진행 중`
- 현재 선택된 Tarkov 게임 진행 프로필을 기준으로 현재 수행 가능한 퀘스트를 보여줍니다.
- 사용자는 퀘스트를 완료 처리할 수 있고, 완료 기록은 후속 퀘스트 해금 판정에 반영됩니다.
- 사용자는 퀘스트의 설명/목표 등 클리어에 필요한 정보를 보고 Wiki 페이지를 열 수 있어야 합니다.
- 퀘스트 목록은 장소(맵) 또는 상인 기준으로 분류해서 볼 수 있어야 합니다.

### FEATURE-002 — 은신처 목록

- 상태: `INTENT_CAPTURED`
- 은신처 시설 목록을 보여주고 사용자가 시설 레벨을 설정할 수 있기를 원합니다.
- 구체적인 동작은 추후 협의합니다.

### FEATURE-003 — 필요 아이템

- 상태: `INTENT_CAPTURED`
- 은신처 업그레이드 및 퀘스트에 필요한 아이템 목록을 다루며 사용자는 보유 개수를 기록할 수 있기를 원합니다.
- 필요 수량 계산과 진행도 연동은 추후 협의합니다.

### FEATURE-004 — 탄약 표

- 상태: `INTENT_CAPTURED`
- 구경별 탄약 목록과 각 탄약의 정보·수급처 등을 표로 확인할 수 있기를 원합니다.
- 구체적인 정보 항목과 동작은 추후 협의합니다.

### FEATURE-005 — 지도

- 상태: `INTENT_CAPTURED`
- 지도에서 각종 정보를 확인하고, 미니맵 형식으로 띄워 인게임 중에도 사용할 수 있기를 원합니다.
- 구체적인 동작은 추후 협의합니다.

### FEATURE-006 — RatScanner 기능 통합

- 상태: `INTENT_CAPTURED / LATER`
- RatScanner의 기능을 준현 헬퍼로 옮기고 싶어 합니다.
- 현재 원본 프로그램이 정상 작동하지 않아 후속 단계로 둡니다.

## 5. 제품 설계 방식

1. 사용자가 기능의 목적과 원하는 경험을 구두로 설명합니다.
2. 개발자가 자신의 이해를 제품 관점에서 다시 설명하고 필요한 경우 역제안합니다.
3. 사용자가 잘못 이해한 부분과 빠진 부분을 교정합니다.
4. 실제 작동 방식을 구체화합니다.
5. 의미와 동작이 충분히 맞았을 때만 공식 Flow와 Requirement로 기록합니다.

## 6. 퀘스트 핵심 사용 흐름

### FLOW-001 — 현재 가능한 퀘스트 확인 및 완료 동기화

- 상태: `CONFIRMED`
- 시작 상황: 사용자가 준현 헬퍼의 퀘스트 기능을 엽니다.
- 사용자 목표: 실제 게임의 현재 캐릭터 상태에서 수행 가능한 퀘스트와 준현 헬퍼의 목록을 최대한 일치시킵니다.
- 사용자의 입력/행동: 선택된 게임 진행 프로필의 캐릭터 정보를 관리하고, 게임에서 퀘스트를 완료하면 준현 헬퍼에서도 완료 처리합니다.
- 프로그램의 동작: 해당 게임 모드의 전체 퀘스트 데이터와 현재 프로필의 캐릭터 상태/퀘스트 기록을 비교하여 선행 조건을 만족한 미완료 퀘스트를 계산합니다.
- 프로그램의 출력: 실제 게임에서 수주 가능한 퀘스트를 준현 헬퍼에서는 이미 수락된 `현재 퀘스트`로 보여줍니다.
- 완료 조건: 게임에서 퀘스트 완료 → 준현 헬퍼에서 완료 처리 → 후속 퀘스트 해금 판정 갱신.

## 7. 퀘스트 제품 요구사항

### REQ-001 — 현재 퀘스트 자동 판정

- 상태: `CONFIRMED`
- 사용자 의도: 전체 퀘스트가 아니라 현재 자신의 캐릭터가 실제 게임에서 수행할 수 있는 퀘스트를 보고 싶습니다.
- 요구 동작: 준현 헬퍼는 최신 퀘스트 데이터의 선행 조건과 현재 선택된 게임 진행 프로필의 상태를 비교하여, 조건을 만족하고 아직 완료되지 않은 퀘스트를 자동으로 계산해야 합니다.
- 수락 처리: 실제 게임의 `잠김 → 수주 가능 → 진행 중` 중 준현 헬퍼는 수주 가능한 퀘스트를 모두 수락한다고 가정합니다.
- 준현 헬퍼 상태: `잠김 → 현재 퀘스트 → 완료`.
- 관련 Flow: `FLOW-001`

### REQ-002 — 퀘스트 완료 동기화

- 상태: `CONFIRMED`
- 사용자가 퀘스트를 완료 처리하면 선택된 진행 프로필에 완료 상태를 저장하고, 후속 퀘스트의 해금 판정을 다시 계산해야 합니다.
- 관련 Flow: `FLOW-001`

### REQ-003 — 게임 모드별 독립 진행 프로필

- 상태: `CONFIRMED`
- PvP, PvE, 시즌 계열 등 서로 다른 Tarkov 캐릭터는 서로 독립된 게임 진행 프로필로 관리합니다.
- 각 프로필에는 해당 캐릭터의 레벨, 진영, 평판/로열티, 에디션, 프레스티지, 완료 퀘스트 등 해금 판정에 필요한 상태를 저장할 수 있어야 합니다.
- 실제 최신 퀘스트 데이터에서 추가 조건이 확인되면 필요한 프로필 필드와 판정 규칙을 확장합니다.

### REQ-004 — 퀘스트 원천 데이터 변환 계층

- 상태: `CONFIRMED`
- `json.tarkov.dev`에서 각 게임 모드에 맞는 최신 퀘스트 데이터를 받아 준현 헬퍼 내부 퀘스트 모델로 변환하여 사용합니다.
- 제품 로직과 UI가 외부 API 원본 스키마에 직접 종속되지 않도록 합니다.

### REQ-005 — 시간 지연 해금은 판정에서 제외

- 상태: `CONFIRMED`
- `AvailableAfter`처럼 다른 조건을 만족한 뒤 일정 시간이 지나야 실제 게임에서 등장하는 시간 지연은 준현 헬퍼의 퀘스트 해금 판정에 사용하지 않습니다.
- 이유: 준현 헬퍼는 게임에서 실제 선행 퀘스트가 완료된 정확한 시각을 알 수 없으며, 사용자가 늦게 완료 체크하면 타이머가 실제 게임과 어긋날 수 있습니다.
- 동작: 시간 지연 외의 확인 가능한 선행 조건을 만족하면 준현 헬퍼에서는 해당 퀘스트를 현재 퀘스트로 보여줍니다.
- 결과: 시간 지연이 있는 일부 퀘스트는 실제 게임보다 일찍 보일 수 있으며 이는 의도된 차이입니다.

## 8. 퀘스트 해금 판정에 사용할 조건

목표는 **현재 선택된 캐릭터가 실제 게임에서 선행 조건을 만족하여 수행할 수 있는 퀘스트를 최대한 동일하게 계산하는 것**입니다.

현재 확인/예상된 조건 계열:

- 캐릭터 레벨
- 진영(BEAR/USEC)
- 선행 퀘스트 상태
- 상인 평판(Standing)
- 상인 로열티 레벨(Loyalty Level)
- 게임 에디션/버전별 제한
- 프레스티지
- 선택된 게임 모드에 따른 퀘스트 데이터
- 이벤트/시즌 등 퀘스트 노출에 영향을 주는 전역 조건이 데이터로 안정적으로 판정 가능할 경우 해당 조건

시간 지연은 명시적으로 제외합니다.

실제 `json.tarkov.dev`가 각 조건을 어떤 형태로 제공하는지 구현 전 데이터 검증을 수행합니다. 외부 데이터로 판정할 수 없는 조건은 임의로 정확하다고 가정하지 않습니다.

## 9. 퀘스트 표시/탐색

현재 제품 수준에서 합의된 동작:

- 장소(맵) 또는 상인 기준으로 분류 가능
- 퀘스트를 선택해 설명/목표 등 클리어에 필요한 정보 확인 가능
- Wiki 페이지 열기 가능

카드, 표, 패널 배치 등 **시각적 UI 형태는 현재 확정하지 않습니다.** 기능적 요구사항이 정리된 뒤 구현 단계에서 가장 적합한 형태를 개발자가 설계·제안합니다.

## 10. 퀘스트 비목표

- 인게임에서 퀘스트를 `Accept`했는지 별도로 추적하지 않습니다.
- 준현 헬퍼에서 퀘스트마다 별도의 수락 조작을 요구하지 않습니다.
- 실제 게임의 시간 지연 해금 타이머를 재현하지 않습니다.
- 현재 단계에서 퀘스트 화면의 시각적 레이아웃을 고정하지 않습니다.

## 11. 퀘스트 UX 원칙

- 인게임과 준현 헬퍼를 맞추기 위해 필요한 사용자 입력을 최소화합니다.
- 데이터와 프로필로 계산 가능한 상태는 프로그램이 자동으로 계산합니다.
- 사용자는 게임에서 발생한 핵심 상태 변화(예: 퀘스트 완료)를 준현 헬퍼에 반영하는 데 집중합니다.

## 12. 정보 정확성 원칙

`CONFIRMED`

- 기존 Tarkov-Helper에 구현되어 있다는 이유만으로 정보를 사실로 간주하지 않습니다.
- 게임 정보가 제품 동작에 영향을 주는 경우 최신 출처와 갱신 방식을 별도로 정의합니다.
- 불확실하거나 오래될 수 있는 정보는 검증 없이 제품 규칙으로 고정하지 않습니다.
- 외부 데이터가 실제 게임 상태를 완전히 재현할 수 없는 경우 그 차이를 명시적으로 설계합니다.

## 13. 현재 퀘스트 설계의 다음 초점

퀘스트의 핵심 목적, 데이터 원천, 게임 모드별 독립 프로필, 현재 퀘스트 판정, 완료 동기화, 시간 지연 제외 원칙까지 합의되었습니다.

다음에는 필요에 따라 다음을 검토합니다.

- `json.tarkov.dev`가 실제 해금 조건을 어디까지 제공하는지 최종 대조
- 실패/분기형 선행 퀘스트 상태를 어떤 방식으로 보정할지
- 완료 처리 취소/오입력 복구 방식
- API 갱신/캐시/오프라인 처리 방식

시각적 퀘스트 UI 설계는 현재 단계에서 보류합니다.
