# PRODUCT — 준현 헬퍼 제품 정의

이 문서는 **무엇을 만들고 왜 만드는지**를 정의하는 제품의 공식 제품 설계 문서입니다.

사용자가 구두로 전달한 아이디어는 곧바로 완성된 요구사항으로 간주하지 않습니다. 먼저 원래 의도를 기록하고, 개발자의 해석을 사용자와 맞춘 뒤, 실제 작동 방식까지 합의된 내용만 `CONFIRMED` 요구사항으로 승격합니다.

## 1. 제품 이름

`CONFIRMED`

**준현 헬퍼**

저장소 이름은 `JunhyunHelper`이지만 사용자에게 보이는 공식 제품명은 **준현 헬퍼**입니다.

## 2. 제품의 현재 이해

`INTENT_CAPTURED`

준현 헬퍼는 Escape from Tarkov 플레이를 보조하기 위한 데스크톱 헬퍼 프로그램입니다.

현재 사용자가 제시한 주요 기능 영역은 퀘스트 목록, 은신처 목록, 필요 아이템, 탄약 표, 지도, RatScanner 기능 통합입니다.

이 문장은 **현재까지 전달받은 방향을 요약한 것**이며, 각 기능의 의미·사용 상황·세부 동작이 모두 확정되었다는 뜻은 아닙니다.

## 3. 대상 사용자

`CONFIRMED`

최초 설계 기준 사용자는 이 프로젝트의 사용자 본인입니다. 일반 사용자 확장 여부는 이후 별도로 결정합니다.

## 4. 사용자에게서 직접 전달받은 초기 기능 의도

아래 항목은 아직 정식 요구사항이 아니라 **구두 의도를 보존하기 위한 출발점**입니다.

### FEATURE-001 — 퀘스트 목록

- 상태: `INTENT_CAPTURED`
- 사용자는 조건에 맞는 퀘스트 목록을 볼 수 있기를 원합니다.
- 사용자는 퀘스트를 완료 처리할 수 있기를 원합니다.
- 어떤 조건, 어떤 정보, 어떤 완료 처리 흐름을 원하는지는 아직 사용자와 맞춰야 합니다.

### FEATURE-002 — 은신처 목록

- 상태: `INTENT_CAPTURED`
- 사용자는 은신처 시설 목록을 볼 수 있기를 원합니다.
- 사용자는 시설 레벨을 설정할 수 있기를 원합니다.
- 어떤 정보와 조작 방식이 필요한지는 아직 사용자와 맞춰야 합니다.

### FEATURE-003 — 필요 아이템

- 상태: `INTENT_CAPTURED`
- 은신처 업그레이드 및 퀘스트에 필요한 아이템 목록을 다루는 기능입니다.
- 사용자는 각 아이템의 보유 개수를 추가할 수 있기를 원합니다.
- 필요 수량 계산, 진행도 반영, 분류, 표시 방식 등은 아직 사용자와 맞춰야 합니다.

### FEATURE-004 — 탄약 표

- 상태: `INTENT_CAPTURED`
- 사용자는 구경별 탄약 목록을 확인하고 싶어 합니다.
- 각 탄약의 정보와 수급처 등을 표로 확인하고 싶어 합니다.
- 정확한 정보 항목과 실제 사용 방식은 아직 사용자와 맞춰야 합니다.

### FEATURE-005 — 지도

- 상태: `INTENT_CAPTURED`
- 사용자는 지도에서 각종 정보를 확인하고 싶어 합니다.
- 지도를 미니맵 형식으로 띄워 인게임 중에도 사용하고 싶어 합니다.
- 지도 정보의 종류, 조작 방식, 미니맵의 동작은 아직 사용자와 맞춰야 합니다.

### FEATURE-006 — RatScanner 기능 통합

- 상태: `INTENT_CAPTURED / LATER`
- 사용자는 RatScanner의 기능을 준현 헬퍼로 옮기고 싶어 합니다.
- 현재 RatScanner 원본 프로그램이 정상 작동하지 않아 실제 통합은 후속 단계로 계획합니다.
- 어떤 RatScanner 기능을 유지할지와 구현 방식은 추후 별도로 협의·조사합니다.

## 5. 제품 설계 방식

각 기능은 다음 순서로 설계합니다.

1. 사용자가 기능의 목적과 원하는 경험을 구두로 설명합니다.
2. 개발자가 자신의 이해를 제품 관점에서 다시 설명합니다.
3. 사용자가 잘못 이해한 부분과 빠진 부분을 교정합니다.
4. 실제 작동 방식을 대화로 구체화합니다.
   - 언제 사용하는가
   - 무엇을 보는가
   - 무엇을 입력/조작하는가
   - 프로그램이 무엇을 판단/계산하는가
   - 무엇을 화면에 보여주는가
   - 다른 기능과 어떤 관계가 있는가
   - 어떤 예외 상황이 있는가
5. 의미와 동작이 충분히 맞았을 때만 정식 Flow와 Requirement를 `CONFIRMED`로 기록합니다.

## 7. 제품 요구사항

현재 **세부 제품 요구사항은 아직 확정하지 않았습니다.**

이전의 짧은 기능 설명을 곧바로 `REQ-XXX CONFIRMED`로 변환하는 방식은 사용하지 않습니다. 기능별 의도 정렬과 작동 방식 협의가 끝난 뒤 요구사항을 작성합니다.

## 8. 기능 간 관계

현재: `OPEN`

퀘스트, 은신처, 필요 아이템 등이 서로 연결될 가능성은 있으나, 연결 방식은 사용자와 기능별 작동을 먼저 맞춘 뒤 정의합니다.

기존 Tarkov-Helper의 연동 방식을 기본값으로 삼지 않습니다.

## 9. 비목표(Non-goals)

현재: `OPEN`

## 10. UX 원칙

현재: `OPEN`

각 기능의 실제 사용 상황과 사용자가 기대하는 조작 방식을 대화로 확인한 뒤 확정합니다.

## 11. 정보 정확성 원칙

`CONFIRMED`

- 기존 Tarkov-Helper에 표시되거나 구현되어 있다는 이유만으로 정보를 사실로 간주하지 않습니다.
- 게임 정보가 제품 동작에 영향을 주는 경우 출처와 갱신 방식을 별도로 정의해야 합니다.
- 불확실하거나 오래될 수 있는 정보는 검증 없이 제품 규칙으로 고정하지 않습니다.
- RatScanner 또한 원본 구현을 그대로 정답으로 복제하지 않고, 사용자에게 필요한 기능을 다시 정의한 뒤 준현 헬퍼 설계에 맞게 통합합니다.

## 12. 현재 제품 설계의 다음 초점

기능 간 자동 연동 규칙부터 정하지 않습니다.

먼저 **준현 헬퍼 전체에 대해 개발자가 이해한 방향이 사용자의 의도와 맞는지 확인**하고, 그 다음 각 기능을 하나씩 선택해 목적과 실제 작동 방식을 대화로 설계합니다.
